1. System-Architektur: Das lokale Nervensystem

Die Architektur von Open Brain ist kompromisslos nach dem Prinzip der Separation of Concerns (Trennung der Zuständigkeiten) entworfen. Anstatt einer monolithischen Anwendung besteht das System aus dedizierten Microservices. Dies ist eine technische Notwendigkeit, um die asymmetrischen Hardware-Anforderungen (CPU-Last für Embeddings, GPU-Last für LLM-Inferenz, I/O-Last für die Datenbank) isoliert skalieren zu können.

1.1 Die Layer-Struktur

Das System operiert in vier streng getrennten horizontalen Schichten:

  • Persistence Layer (Datenhaltung): Hier liegt das persistente Wissen. Die PostgreSQL-Datenbank ist passiv, zustandslos hinsichtlich der KI-Logik und speichert ausschließlich Vektoren und JSONB-Strukturen hochgradig optimiert.
  • Abstraction Layer (Schnittstellen): PostgREST und das Nginx-Gateway abstrahieren die Datenbank zu einer RESTful-API. Dies entkoppelt die Datenbank-Clients von SQL-Spezifika.
  • Inference Layer (Intelligenz): Ollama (Embeddings) und LM Studio (LLM) fungieren als zustandslose Inference-Engines. Sie erhalten Prompts, berechnen Tensoren und liefern Resultate, ohne jeglichen State zu halten.
  • Application Layer (Interaktion & Agentik): Der MCP-Server und die Agenten-Bots implementieren die Geschäftslogik. Sie orchestrieren den ReAct-Loop (Reasoning and Acting) und entscheiden, welche Tools in welcher Reihenfolge ausgeführt werden.

1.2 Das Docker-Netzwerk und Container-Topologie

Auf Netzwerkebene existieren alle Container in einem isolierten virtuellen Docker-Bridge-Netzwerk namens openbrain_default. Die interne Namensauflösung erfolgt über den Docker-DNS (z.B. http://db:5432). Nach außen ist das Netzwerk strikt isoliert. Jeglicher externe Traffic (z.B. vom Host-Browser zum Supabase Studio) muss explizit über Port-Mappings geschleust werden, was eine erste "Zero-Trust"-Barriere etabliert.

Die Container-Abhängigkeiten sind wie folgt definiert:

  • Die Daten-Basis: openbrain-db (PostgreSQL 17). Ausschießlich intern für postgrest und meta erreichbar.
  • API & Orchestrierung: gateway (Nginx) fungiert als zentraler Reverse-Proxy. Er transformiert /rest/v1/ Anfragen via URL-Rewriting zu sauberen postgrest Calls und managt CORS-Header zentral.
  • KI & Agenten: Pro Agent laufen zwei Container: mcp-server (Tool-Hub) und agent-bot (ReAct-Loop). Agenten-Identität kommt ausschließlich aus config.yaml — nie hartkodiert.
  • The Nexus: nexus-broker (Mosquitto MQTT, Port 1883) ist der asynchrone Kommunikations-Bus. nexus-service (Port 7734) loggt jede Nachricht. nexus-frontend (Port 7733) ist das Admin-Dashboard.

2. Die Daten-Schicht: Die 3-Saeulen-Architektur

Das Open Brain nutzt eine spezialisierte 3-Saeulen-Architektur, um maximale Uebersichtlichkeit und Kontext-Trennung zu gewaehrleisten. Wir nutzen PostgreSQL 17 mit pgvector, verzichten aber bewusst auf Datenbank-interne RLS-Logik zugunsten von expliziter Filter-Logik im Code.

2.1 Die 3 Saeulen

1. open_brain (Valuable Thoughts)

Diese Tabelle beherbergt das eigentliche Langzeitgedaechtnis. Sie ist optimiert fuer semantische Suche und Deduplizierung.

  • agent_id: Identifiziert den Eigentuemer des Gedankens.
  • thought_type: Klassifizierung (z.B. observation, task, idea).
  • content_hash: SHA256-Hash zur kryptografischen Deduplizierung.
  • embedding: Der semantische VECTOR(4096).

2. agent_workspace (Raw Data & Scrapes)

Ein isolierter Bereich für externe Datenimporte und temporäre Arbeits-Artefakte (z.B. X-Posts). Verhindert, dass das open_brain durch Massendaten-Importe "verrauscht". Diese Tabelle ist optimiert für Massendaten-Speicherung und bietet Platz für Rohdaten und deren semantische Vektoren.

3. nexus_chat (Communication Log)

Der zentrale Audit-Trail aller MQTT-Nachrichten und System-Events. Jede Kommunikation zwischen Agenten sowie alle System-Benachrichtigungen (Absender system) werden hier dauerhaft persistiert. Dies garantiert, dass auch automatisierte Statusmeldungen (z.B. Sync-Abschluss) nach einem Neuladen des Dashboards in der Historie erhalten bleiben.

Deep-Dive: Dynamische JSONB-Iterierung (Code-Free Configuration)

Das Architekturziel von Open Brain ist es, dass sich Agenten ausschließlich durch ihre Text-Konfiguration (Prompts) unterscheiden dürfen. Um dies zu gewährleisten, ist die Code-Basis des MCP-Servers 100% dynamisch aufgebaut. Wenn ein Agent-Tool (z.B. search_thoughts) Resultate aus der Datenbank liest, iteriert es programmatisch über alle Keys im JSONB-Objekt, ohne dass bestimmte Felder wie people hartkodiert wären:


for (const [key, val] of Object.entries(m)) {
  if (key === "source" || key === "type") continue; // Interne Felder
  if (Array.isArray(val) && val.length > 0) {
    parts.push(`${key}: ${val.join(", ")}`);
  } else if (typeof val === "string" || typeof val === "number") {
    parts.push(`${key}: ${val}`);
  }
}

Die Konsequenz für Entwickler: Da die Datenbank JSONB nicht limitiert und der Code dynamisch iteriert, hast du bei der Agenten-Erstellung völlige Freiheit. Ein Koch-Bot kann in seinem Metadaten-Prompt anweisen, völlig neue Arrays wie "zutaten": ["Mehl", "Zucker"] zu extrahieren. Diese werden sauber als JSONB gespeichert und bei einer späteren LLM-Suche automatisch formatiert an den Bot zurückgeliefert. Keine einzige Zeile TypeScript-Code muss dafür verändert werden.

2.2 Spezialisierte Such-Architektur (Semantik vs. Exakt)

Die Architektur trennt die Suche strikt in zwei hochspezialisierte Werkzeuge, um "False Positives" (z.B. "sievers" bei der Suche nach dem Ticker "SIVE") zu eliminieren:

  • Semantische Suche (semantic_search_workspace): Führt reinen Vektorvergleich (<=>) durch. Nutzt Ollama-Embeddings, um inhaltlich verwandte Themen (z.B. "Laser" bei der Suche nach "Photonics") zu finden, ignoriert aber harte Textübereinstimmungen.
  • Exakte Keyword-Suche (exact_search_workspace): Nutzt native PostgreSQL-JSONB-Operatoren (@>) für strukturierte Metadaten (Tickers, Authors) UND ergänzend einen case-insensitiven ILIKE-Abgleich über den kompletten Post-Inhalt. Dies kombiniert die Präzision harter Wortgrenzen in Metadaten mit der Flexibilität einer globalen Volltextsuche.

2.2.1 Token-Optimierung via Return Modes & Snippets

Um das Kontext-Fenster des LLM bei umfangreichen Suchergebnissen (z.B. hunderte X-Posts) nicht zu überlasten, verfügen die Suchwerkzeuge über einen return_mode Parameter:

  • snippets (Default): Schneidet den Fließtext nach 150 Zeichen ab, fügt den Autor hinzu und entfernt irrelevante Metadaten. Dies reduziert den Token-Verbrauch drastisch und liefert dem LLM einen schnellen Überblick.
  • ids_only: Liefert ausschließlich die Datenbank-IDs zurück. Ideal für reine Zählungen.
  • full_text: Gibt den gesamten Inhalt inkl. Metadaten zurück. Nur zu verwenden, wenn absolut nötig.

Sollte das LLM aufgrund eines Snippets erkennen, dass es den ganzen Text analysieren muss, nutzt es das dedizierte Werkzeug read_workspace_posts([ids]), um die gewünschten Dokumente explizit und ungeschwärzt in voller Länge nachzuladen.

2.2.2 Telemetrie und Chronologie

Zusätzlich zur LLM-Ausgabe erzeugt der MCP-Server detaillierte Such-Telemetrie für das Nexus-Dashboard. Ergebnisse werden serverseitig nach Tagen aggregiert, sodass der Nutzer im Live-Chat sofort eine Aufschlüsselung sieht (z.B. 10 Treffer gesamt: 2 am 14.05., 8 am 15.05.), sortiert mit dem neuesten Datum als letzte Zeile.

2.2.3 Trend-Erkennung & Erste Erwähnungen (First Mentions)

Um frühzeitig Hypes oder neue Trends in den Daten zu identifizieren, verfügt das System über das spezialisierte MCP-Werkzeug find_first_keyword_mentions. Anstatt lediglich die neuesten Posts aufzulisten, sucht dieses Tool den historischen "Nullpunkt" für beliebige Buzzwords.

  • Funktionsweise (SQL CROSS JOIN): Der Agent übergibt dem Tool ein JSON-Array mit Keywords (z.B. ["AI", "FURUYA", "Auros"]). Die PostgreSQL-Funktion führt einen CROSS JOIN über diese Keywords mit einem Volltext-ILIKE-Abgleich über alle X-Posts aus und filtert pro Wort den chronologisch allerersten Treffer (ORDER BY published_at ASC).
  • Direct-Dump Mechanismus: Da es pro Keyword ohnehin nur einen wahren ersten historischen Post gibt, lädt der MCP-Server diesen Post nicht in den Kontext des Agenten, sondern umgeht die LLM-Inferenz völlig. Das Tool nutzt sendTelemetry, um den gefundenen Original-Post inkl. Zeitstempel und Autor direkt in den Live-Chat des Nexus zu werfen, was Halluzinationen zu 100% ausschließt und extrem schnell ist.

3. Die API-Schicht: PostgREST & Automatisierung

Anstatt Backend-Code in Node.js zu schreiben, um SQL in JSON zu konvertieren, nutzen wir PostgREST. Dieser binäre Haskell-Service läuft neben der Datenbank, analysiert das Schema zur Laufzeit und stellt on-the-fly REST-Endpunkte für alle Tabellen und RPCs bereit. Maximale Performance, null Boilerplate.

3.1 Die Rolle des Authenticator

PostgREST basiert auf nativem PostgreSQL Row-Level-Security (RLS). Bei eingehenden HTTP-Requests wird ein SET ROLE in der Datenbank ausgeführt:

  1. anon: Der Default-State. Zugriff nur auf öffentlich definierte Views.
  2. authenticator: Der Verbindungs-User für PostgREST selbst (hat keine Datenzugriffe).
  3. service_role: Die Administrative Bypass-Rolle. Der MCP-Server autorisiert sich über diese Rolle, um den RLS-Schutz für Schreiboperationen zu umgehen.

3.2 JWT-Sicherheit

Sicherheit ist kryptografisch durch JSON Web Tokens (JWT) gesichert. Jeder HTTP-Request des MCP-Servers injiziert einen Bearer-Token, der via HMAC-SHA256 mit dem JWT_SECRET signiert ist. Die Datenbank validiert die Signatur und setzt die User-Role entsprechend. Es gibt keine Schwachstellen durch unsichere API-Keys.

4. Die Administrations-Schicht: Supabase Studio & Meta

Trotz der 100% lokalen ("Air-Gapped") Ausführung nutzen wir das grafische Frontend von Supabase. Es handelt sich um ein vollständiges lokales Deployment ihrer Open-Source-Architektur, nicht um eine Cloud-Anbindung.

4.1 Das Dashboard (Port 3000)

Das Supabase Studio ist im Grunde ein modernes, webbasiertes pgAdmin oder DBeaver, geschrieben in Next.js. Da die Agenten ihre Metadaten als komplexe JSONB-Objekte speichern, ist eine reine Terminal-Ansicht (psql) oft ineffizient. Über Port 3000 erhältst du eine grafische Tabellenansicht. Generiert das LLM ein fehlerhaftes JSON, lässt sich der State hier direkt auf Datenbank-Ebene patchen und debuggen. Zudem liefert es Werkzeuge zur Analyse von SQL-Logs und Query-Performance.

4.2 Der meta-Service (Introspektions-Abstraktion)

Der Meta-Container ist eine notwendige Abstraktionsschicht für das Supabase Studio. Da das Next.js Frontend nicht direkt über ein SQL-Protokoll mit PostgreSQL kommuniziert, stellt der Meta-Service die erforderliche HTTP-REST-Schnittstelle für die Schema-Analyse bereit.

Der Service greift auf das information_schema von Postgres zu und übersetzt die interne SQL-Struktur in eine JSON-API. Dies ermöglicht dem Studio, Tabellen und Spalten dynamisch zu rendern, ohne die Datenbank direkt abfragen zu müssen.

5. Die Embedding-Schicht: Ollama & Vektorisierung

Während klassische SQL-Suchen (ILIKE) bei semantischen Verknüpfungen versagen, löst Ollama das NLP-Problem (Natural Language Processing) durch lokale Tensor-Berechnungen in Echtzeit.

5.1 Semantische Transformation mit Ollama

Ollama wird isoliert für spezialisierte Embedding-Modelle (z.B. Qwen3-Embedding-8B) eingesetzt. Diese Modelle transformieren Texte extrem ressourceneffizient in dichte Vektor-Räume, wodurch die GPU-Kapazität für die primäre LLM-Inferenz (via LM Studio) optimiert wird.

5.2 Der Prozess der Vektorisierung

Der MCP-Server piped den Text via REST an Ollama. Ollama tokenisiert den String, führt einen Forward-Pass durch das neuronale Netz aus und liefert ein 4096-dimensionales Float-Array zurück. Dieser Vektor ist die mathematische Signatur der Bedeutung. Ollama hält dabei keinen State und speichert keine Nutzerdaten.

6. Die Proxy-Schicht: Nginx - Der Dirigent des Netzwerkverkehrs

Der Nginx-Container läuft als asynchroner Event-Driven Reverse Proxy. Er ist der unüberwindbare Checkpoint zwischen den Microservices und der Außenwelt. Aber was bedeutet das im Kontext dieser Applikation genau?

6.1 Proxy vs. Reverse Proxy

Ein klassischer Proxy (z.B. in einem Firmennetzwerk) maskiert den Client: Der angerufene Server weiß nicht, welcher Rechner die Webseite tatsächlich angefordert hat. Ein Reverse Proxy dreht dieses Prinzip um: Er maskiert die Backend-Infrastruktur gegenüber dem aufrufenden Client.

In Open Brain laufen verschiedene Dienste (z.B. PostgREST für die API, Meta für das Schema). Anstatt all diese internen Ports wild im Docker-Netz nach außen zu öffnen, bündelt Nginx alles auf einem einzigen zentralen Eingangspunkt (Port 8001). Jeder Request von außen landet zuerst bei Nginx, der ihn prüft und an den richtigen internen Container weiterleitet. Das reduziert die Angriffsfläche signifikant und ermöglicht zentrales Logging.

6.2 Pfad-Harmonisierung (Was macht das SDK?)

Der MCP-Server interagiert mit der Datenbank über das Supabase-SDK (Software Development Kit). Ein SDK ist eine Bibliothek abstrahierter Funktionen, die API-Aufrufe kapselt. Da dieses spezifische SDK für den produktiven Betrieb in der Supabase-Cloud entworfen wurde, implementiert es hartkodierte API-Routen wie /rest/v1/.

Da unsere Infrastruktur vollständig lokal operiert, existiert dieser URI-Namespace nicht nativ. Nginx übernimmt an dieser Stelle das Path-Rewriting: Initiiert das SDK einen HTTP-Request an /rest/v1/thoughts, interceptiert Nginx diesen, entfernt per Regex das Cloud-Präfix und delegiert den modifizierten Request an den lokalen postgrest-Container. Durch diese Emulation der Cloud-API-Struktur auf Netzwerkebene entfällt die Notwendigkeit, den Quellcode der externen npm-Pakete forken und patchen zu müssen.

6.3 CORS-Management & Preflight-Requests

Das CORS (Cross-Origin Resource Sharing) Protokoll ist ein Sicherheitskonzept von Web-Browsern. Es blockiert standardmäßig clientseitige HTTP-Anfragen, wenn die anfordernde Domain (hier: Studio auf Port 3000) nicht mit der Ziel-Domain (hier: PostgREST auf Port 3001) identisch ist.

Bei Cross-Origin-Szenarien führt der Browser vor dem eigentlichen Request zwingend einen Preflight-Request (HTTP-Methode OPTIONS) aus, um die autorisierten Origins des Zielservers abzufragen. Um die internen Microservices nicht mit der Implementierung von Frontend-Sicherheitsprotokollen zu belasten, terminiert Nginx diese Preflight-Requests zentral. Nginx fängt den OPTIONS-Call ab und beantwortet ihn direkt durch Injektion des Access-Control-Allow-Origin Headers. Der Browser wertet die HTTP-Response aus, autorisiert die Verbindung und führt den eigentlichen Request durch, während die Backend-Container von der CORS-Logik vollständig entkoppelt bleiben.

7. The Nexus: MQTT-basierter Agenten-Kommunikations-Hub

The Nexus fungiert als asynchrones Kommunikations-Rückgrat des Systems. Der zentrale Mechanismus ist ein MQTT Message Broker (Mosquitto).

7.1 MQTT als Kommunikations-Rückgrat

Der zentrale Kommunikations-Mechanismus basiert auf dem asynchronen MQTT-Protokoll (ISO/IEC 20922). Dies ermöglicht eine leichtgewichtige Pub/Sub-Kommunikation mit minimaler Latenz (<5ms) und persistenter TCP-Verbindung.

7.2 Cross-Agent MCP via MQTT

Will Agent A ein Tool von Agent B nutzen, publiziert er auf agents/B/mcp/request. Agent B führt das Tool aus und antwortet auf agents/A/mcp/response/{req_id}. Kein Agent kennt die HTTP-URL eines anderen. Der Nexus-Service loggt jeden Cross-Agent-MCP-Call mit msg_type: mcp_request.

7.3 Multi-Provider Management: Dynamische LLM-Orchestrierung

Open Brain verfolgt einen hybriden Ansatz bei der Modell-Inferenz. Während die lokale Ausführung (LM Studio) das Standard-Szenario ist, erlaubt das System die nahtlose Zuschaltung von Cloud-Modellen wie Google Gemini für ressourcenintensive Aufgaben. Dieses "Brain-Swapping" erfolgt ohne System-Neustart.

7.3.1 Zentrale Zustandsverwaltung (system_settings)

Die Konfiguration der LLM-Provider wird in der dedizierten Datenbank-Tabelle system_settings persistiert. Das System speichert hier ein JSON-Objekt (provider_config), welches jedem Agenten (ID) seinen aktuellen Provider zuweist (z.B. {"ea": "local", "cco": "gemini"}). Dies garantiert, dass die gewählte Konfiguration auch nach einem Container-Neustart erhalten bleibt.

7.3.2 Real-Time Switching via MQTT

Die Umschaltung der Intelligenz erfolgt asynchron und in Echtzeit über den Nexus-Bus:

  1. Dashboard-Trigger: Der Nutzer wählt im Nexus-Frontend einen neuen Provider für einen Agenten aus.
  2. API-Broadcast: Der nexus-service aktualisiert den Wert in der Datenbank und publiziert simultan eine Nachricht auf dem Topic system/config/provider.
  3. Agenten-Hot-Swap: Der betroffene Agent (EA oder CCO) empfängt die Nachricht, erkennt seine AGENT_ID und wechselt intern sofort den API-Adapter. Die nächste Inferenz-Anfrage wird bereits über das neue Backend geleitet.

7.3.3 Provider-Isolation

Das System unterstützt unterschiedliche Provider pro Agent. So kann beispielsweise der EA-Agent zur Kostenersparnis auf einem kleinen lokalen Modell laufen, während der CCO-Agent für komplexe Marktanalysen temporär auf Gemini 1.5 Pro hochgestuft wird. Dies bietet maximale Flexibilität bei optimaler Ressourcenausnutzung.

7.3.4 LM Studio JIT Loading & Unloading

Das Nexus Dashboard ermöglicht das direkte Laden und Entladen lokaler LLM-Modelle (via LM Studio v1 API). Das "Just-in-Time" (JIT) Loading erfolgt über einen Dummy-Inferenz-Aufruf, der LM Studio zwingt, das Modell in den VRAM zu laden. Ein Klick auf "Unload" nutzt den POST /api/v1/models/unload Endpoint inkl. der Instanz-ID, um Ressourcen im VRAM explizit wieder freizugeben. Dies ermöglicht händisches Speichermanagement, ohne das Dashboard verlassen zu müssen.

7.4 UI-Features & Live-Interaktion

Das Nexus-Frontend bietet spezialisierte Funktionen zur Steuerung des Live-Streams, um die Benutzererfahrung bei hoher Nachrichten-Frequenz zu optimieren.

7.4.1 Auto-Scroll Management

In einem System, in dem mehrere Agenten parallel arbeiten, kann die Scroll-Position im Chat-Fenster unvorhersehbar springen. Um dies zu verhindern, verfügt das Dashboard über einen Auto-Scroll Toggle im Header des Stream-Panes.

  • Active (Standard): Der Chat fokussiert automatisch auf die neueste Nachricht. Ideal für die Live-Überwachung.
  • Inactive (Lesemodus): Der Chat friert die aktuelle Scroll-Position ein. Dies erlaubt es dem Nutzer, in Ruhe ältere Analysen zu lesen, während neue Nachrichten im Hintergrund lautlos angehängt werden.

7.5 Automatische Agenten-Erkennung (Discovery)

Damit neue oder selten genutzte Agenten ohne manuelle Datenbankeinträge oder Dummy-Nachrichten im Dashboard sichtbar werden, nutzt der Nexus eine automatische Erkennung:

  • MQTT Status als Trigger: Beim Starten publiziert jeder Agenten-Bot eine Statusmeldung (status: "online") mit dem Flag retain: true auf dem Topic agents/status. Der MQTT-Broker speichert dieses Statuspaket dauerhaft.
  • Intelligentes Backend-Caching: Beim Systemstart abonniert der nexus-service dieses Topic und erhält sofort alle gespeicherten Statusmeldungen. Die aktiven Agenten-IDs werden im Arbeitsspeicher (_seen_agents) gepuffert.
  • Kombinierter Endpunkt: Der API-Endpunkt /api/agents liest sowohl die historischen Agenten aus der Chat-Datenbank (nexus_chat) als auch die aktuell im Speicher registrierten MQTT-Agenten aus und liefert eine konsolidierte Liste an das Frontend.

8. Der Tool-Server: Deep Dive in die Deno MCP Implementierung

Der MCP-Server ist das technologische Bindeglied zwischen Bot und Datenbank. Er exponiert LLM-lesbare Werkzeuge und orchestriert die Vektorisierung. Wir nutzen hierfür Deno anstelle von Node.js.

Open Brain nutzt ein Template- und Fork-Paradigma. Jeder Agent operiert mit einem dedizierten MCP-Server und einem MQTT-Bot, was eine vollständige Isolation der Identitäten und Toolsets gewährleistet.

Durch die Koppelung eines eigenen MCP-Servers lädt jeder Bot eine individuelle metadata-prompt.txt. Dies verhindert ein globales Schema-Lock-in: Jeder Agent definiert über seinen MCP-Server eine eigene JSONB-Struktur in der Datenbank, ohne Kern-Komponenten oder andere Agenten zu beeinflussen.

8.2 Deep Dive: Die exakte Mechanik von 'capture_thought'

Um die Komplexität hinter einem simplen "Notier dir das" zu entmystifizieren, hier die exakte Code-Mechanik, wenn das capture_thought Tool aufgerufen wird:

  1. Payload-Validierung: Zod validiert den eingehenden JSON-Payload ({ content: string }) streng.
  2. Prompt-Injektion: Der Code führt Deno.readTextFileSync auf der metadata-prompt.txt aus. Er hängt den rohen User-Content an diesen Prompt an.
  3. Strukturierte Inferenz: Ein HTTP POST Request geht an LM_STUDIO_URL/v1/chat/completions. Das LLM wird (meist im JSON-Modus) gezwungen, ausschließlich ein JSON-Objekt zurückzugeben, das dem metadata-prompt entspricht.
  4. Tensor-Berechnung: Parallel oder sequenziell geht ein Request an Ollama (/api/embeddings) um den 4096-Float Vektor zu generieren.
  5. PostgreSQL UPSERT: Ein finaler Request geht an das PostgREST Gateway (/rest/v1/rpc/upsert_thought), der den Text, das generierte JSON-Objekt und das Float-Array transaktionssicher in die DB schreibt.

8.3 Laufzeitumgebung: Deno

  • Security First: Deno läuft standardmäßig in einer Sandbox. Netzwerkzugriffe erfordern explizit --allow-net.
  • Native TypeScript: Kein Webpack, kein Babel. Zero-Config TypeScript-Ausführung.
  • Streamable HTTP (SSE): Der Server nutzt @hono/mcp für Server-Sent Events. Dies ermöglicht Multi-Client-Support über Netzwerkgrenzen hinweg, im Gegensatz zur klassischen stdio-Kommunikation lokaler Skripte.

8.4 Zero-Config Agent Brains (Daten-Isolation)

Anstatt alle Agenten auf einen globalen Wissenspool zugreifen zu lassen, implementiert das System eine strikte Daten-Trennung ("Own Brain" Architektur) auf Metadaten-Ebene. Dies wird komplett ohne Code-Änderungen über die docker-compose.yml gesteuert:

  • AGENT_ID: Wird als Environment Variable an den MCP-Server übergeben. Bei jedem capture_thought wird diese ID automatisch als {"owner": "..."} in die Metadaten injiziert.
  • GLOBAL_BRAIN_ACCESS (false): Der Standard. Der MCP-Server zwingt bei jedem Lesezugriff (Suche, Stats, List) den Filter {"owner": AGENT_ID} auf. Der Agent ist blind für das Wissen anderer Agenten und agiert völlig isoliert.
  • GLOBAL_BRAIN_ACCESS (true): (Z.B. für den Executive Assistant). Der Filter-Zwang entfällt. Dem LLM wird in den Such-Tools stattdessen ein optionaler Parameter owner angeboten. Der Agent kann gezielt die Brains anderer Agenten durchsuchen oder globale Analysen über das gesamte Open Brain fahren.

8.5 X-Integration: Asynchroner Sync & Zero-Duplicate Fetching

Der CCO (Chief Communications Officer) verfügt über das spezialisierte Tool sync_influencer_news, welches eine hochperformante Anbindung an die X-API (v2) implementiert. Da der Abruf und die lokale Vektorisierung von bis zu 500 Posts extrem ressourcen- und zeitaufwändig (LM Studio Inferenz) sind, nutzt das System eine entkoppelte Architektur:

  • Asynchroner Hintergrund-Job: Das Tool bestätigt dem Agenten sofort den Start des Syncs. Die tatsächliche Paginierung, der Download und die Inferenz laufen entkoppelt im Hintergrund. Der Agent wird im Nexus Chat währenddessen nicht blockiert.
  • In-Memory Locking: Um zu verhindern, dass ein ungeduldiger Agent den Abruf für den selben Influencer parallel mehrfach startet, wird eine activeSyncs-Sperre im MCP-Server gehalten.
  • Zero-Duplicate Fetching (`until_id` Trick): Um X-API Kosten zu sparen, verfügt der Sync über eine smarte Lückenfüller-Logik. Bei historischen Abfragen (via start_time) sucht das System zuerst den ältesten bereits gespeicherten Post in der Datenbank. Dieser wird als until_id an X gesendet, wodurch die X-API ausschließlich die fehlende Lücke zurückliefert. Duplikate werden zu 100% vor dem Download verhindert.
  • Live-Telemetrie: Der Hintergrund-Worker meldet via MQTT regelmäßig seinen Fortschritt (z.B. "20 Posts verarbeitet") in den Nexus Chat, bis der Sync abgeschlossen ist.
  • Agenten-Aufweck-Trigger (Asynchrones Feedback): Wenn der langlaufende Hintergrundprozess abschließt, steuert der MCP-Server das LLM nicht direkt auf API-Ebene. Stattdessen nutzt er die interne Nexus-REST-API, um eine gewöhnliche Chat-Nachricht (Absender: "system") auf das private MQTT-Topic des Agenten (z.B. agents/cco/inbox) zu publizieren. Der Agent konsumiert diese Systemnachricht (z.B. "Hintergrund-Sync abgeschlossen. Bitte erstelle die Zusammenfassung.") exakt so, als hätte der menschliche Admin sie im Chat geschrieben. Dies weckt den Agenten auf, fügt den Trigger in seine RAG-Historie ein und startet einen autonomen ReAct-Zyklus zur Erfüllung der Aufgabe. Diese lose Kopplung ist ein massives Architektur-Pattern für lang laufende Agenten-Tasks.

8.5.1 Influencer Management & Mass Sync

Die Verwaltung der X-Accounts erfolgt nicht über statische Listen, sondern über eine intelligente x_influencers Datenbank-Tabelle:

  • Dynamisches Hinzufügen: Über das Tool add_influencer fragt der CCO die X-API nach der User-ID und dem Screen Name ab, vektorisiert die Metadaten und speichert den Account dauerhaft in der Datenbank.
  • Fuzzy Search Sync: Der Befehl sync_influencer_news nutzt die PL/pgSQL-Funktion search_influencers. Wenn ein Agent den Namen "sereni" übergibt, durchsucht PostgreSQL per Vektor-Ähnlichkeit und ILIKE die Datenbank, identifiziert @aleabitoreddit (Screen Name: "serenity") und startet den Sync vollautomatisch.
  • Sequential Mass Sync: Wird sync_influencer_news mit dem Parameter username: "all" aufgerufen, lädt der MCP-Server alle aktiven Accounts aus der Datenbank und arbeitet die Hintergrund-Syncs ressourcenschonend sequenziell (als Batch) ab.
  • Entfernen ohne Datenverlust: Über remove_influencer können Accounts aus der Beobachtungsliste gelöscht werden. Bereits abgerufene Posts im agent_workspace bleiben davon physisch unangetastet, da sie über eigene Metadaten-Zuordnungen persistiert sind.

8.6 System-Telemetrie & Performance-Tracking

Um die Auslastung der KI-Infrastruktur transparent zu machen, generiert jeder MCP-Server Telemetrie-Daten bei LLM- und Embedding-Aufrufen:

  • Metriken: Es werden der exakte Modellname (z.B. google/gemma-4-26b-a4b), die Gesamtzeit der Generierung, die Anzahl der erzeugten Token und die Geschwindigkeit in t/s (Tokens pro Sekunde) gemessen.
  • Echtzeit-Log: Diese Daten werden als Nachricht vom Typ telemetry an den Nexus gesendet und erscheinen unmittelbar im Chat-Verlauf und im Dashboard.

8.7 Direct-Dump: Umgehung der Inferenz bei List-Tasks

Ein wesentliches Architektur-Feature für eine effiziente UI/UX ist der Direct-Dump Mechanismus. Erkennt das System durch strenge Prompt-Direktiven (z.B. durch das Keyword "liste auf"), dass der Benutzer lediglich chronologische Rohdaten sehen will, triggert der MCP Server eine exakte Keyword-Suche (die bei leerem Suchbegriff rein chronologisch absteigend sortiert). Die formatierten Ergebnisse (inkl. Markdown-Escaping) leitet der MCP Server mittels dumpToChat direkt an den Nexus-Chat-Bus weiter. Das LLM erhält daraufhin den systemseitigen [STOP]-Befehl und wird von der Aufgabe entbunden, die Daten selbst zu formatieren. Dies verhindert Halluzinationen und entlastet die Inferenz-Engine.

9. Der Executive Assistant: Bot-Logik, Historie & Agentik

Der agent-ea-bot ist das ausführende Frontend der Intelligenz. Er subscribed seinen MQTT-Topic und steuert den ReAct-Loop.

9.1 Die Zwei-Prompt Strategie

Die Steuerung der Agenten basiert auf einer funktionalen Trennung der Prompts:

  • 1. Der Agenten-Prompt (Das "Wann"): Die prompt.txt im Bot-Container definiert die Persönlichkeit und den Trigger. Sie entscheidet, ob das Werkzeug capture_thought überhaupt gerufen wird.
  • 2. Der Metadaten-Prompt (Das "Wie"): Wie im MCP-Kapitel erklärt, greift erst nach dem Tool-Aufruf die metadata-prompt.txt des MCP-Servers, um den Text strukturiert in JSONB zu formen.

Der Bot operiert in einem autonomen Zyklus: Thought (Tool-Auswahl) → Action (Tool-Aufruf) → Observation (Ergebnis-Analyse). Das System lädt beim Start die letzten 10 Nachrichten aus der nexus_chat-Tabelle, was einen RAG-Mechanismus für den Chat-Status realisiert.

9.3 Multi-Agenten Kommunikation: Tool-Based Delegation

Wenn mehrere Bots (z.B. EA und CCO) auf dem Nexus aktiv sind, muss die Delegation logisch und steuerbar sein. Open Brain nutzt Tool-Based Delegation über den MQTT-Bus:

  • Das 'message_agent' MCP-Tool: Die Delegation erfolgt über das dedizierte MCP-Tool message_agent. Das LLM entscheidet durch Reasoning, ob eine Aufgabe delegiert werden muss. Das Tool übermittelt die Nachricht über die Nexus REST-API in das korrekte Topic.
  • Private Inboxes ohne Mention-Filter: Jeder Agent lauscht exklusiv auf seiner privaten agents/{id}/inbox. Er verarbeitet bedingungslos jede Nachricht, die dort ankommt, da sie explizit an ihn delegiert wurde. Ein Namens-Filter (Mention-Routing) im Text ist nicht mehr nötig.

9.4 Vermeidung von Endlosschleifen (Loop Prevention)

In einem Multi-Agenten-System besteht die Gefahr von Feedback-Loops (Agent A sagt Danke, Agent B sagt Bitte, Agent A sagt Gerne...). Open Brain implementiert hierfür eine strikte Anti-Endlosschleifen-Regel direkt im System-Prompt:

  • Terminierung: Sobald eine Aufgabe erledigt oder eine Information geliefert wurde, muss der Agent die Konversation aktiv beenden, indem er keine weitere Nachricht sendet.
  • Floskel-Filter: Agenten sind angewiesen, nicht auf reine Bestätigungen, Höflichkeitsfloskeln oder "Erledigt"-Meldungen anderer Agenten zu reagieren.

Dieses Paradigma erlaubt es, komplexe Agenten-Ketten zu bilden (Bot A delegiert an Bot B, der delegiert an Bot C), während der Nutzer jeden einzelnen Delegationsschritt transparent im Nexus-Dashboard (Port 7733) verfolgen und eingreifen kann.

9.5 Intercompany Communication (Agent-to-Agent Prompts)

Die Kommunikation zwischen den Agenten (z.B. zwischen CCO und EA) funktioniert nicht auf Basis von Magie, sondern durch präzise Prompt-Architektur. Es ist essenziell, dass Agenten ein klares Konzept haben, an wen sie berichten und wann sie schweigen müssen. Folgende Prompts steuern dieses Verhalten vollständig:

1. Die dynamische Delegations-Regel (Das "An wen")

Die Kommunikation zwischen Agenten erfolgt dynamisch basierend auf dem Absender der ursprünglichen Nachricht. Dies wird durch eine instruktionsbasierte Logik im prompt.txt des Agenten sichergestellt:


**Teamwork & Delegation (IMPORTANT):**
You are part of an agent team. If the 'boss' or the Executive Assistant ('ea') assigns you a task, answer professionally and precisely to the one who asked. 
You MUST use the `message_agent` tool. Make sure to set `target_agent` to the correct agent who requested the task (e.g. "ea" or "boss").

Zweck: Dies lehrt das LLM, den Absender der urprünglichen Nachricht aus der RAG-Chat-Historie zu extrahieren und das Argument target_agent im Tool message_agent entsprechend auf ea oder boss zu setzen.

2. Die absolute Terminierungs-Regel (Das "Wann schweigen")

LLMs sind auf "Hilfsbereitschaft" trainiert. Sie möchten das letzte Wort haben ("Gerne geschehen!", "Aufgabe erledigt!"). In einem MQTT-Bussystem führt das zwingend zu Endlosschleifen, da jede ausgehende MQTT-Nachricht den Trigger für den RAG-Loop des anderen Agenten darstellt. Dies wird durch die [STOP]-Regel hart auf TypeScript-Ebene unterbunden:


**ANTI-INFINITE-LOOP RULE (EXTREMELY IMPORTANT):**
When a task is done, a question is conclusively answered, or a process cannot be completed, actively end the conversation by sending NO further messages.
To do this, you MUST output EXACTLY the word `[STOP]` and absolutely nothing else.
Never reply to pure confirmations or pleasantries (like "Thanks", "Done", or "Task completed") from the other agents.

Zweck: Das LLM wird gezwungen, das explizite Token [STOP] auszugeben, anstatt sich Höflichkeiten auszudenken. Die bot/index.ts fängt diesen String hart ab (if (replyText.trim() === "[STOP]") return;) und bricht die Ausführung ab. Dadurch wird absolut nichts über MQTT publiziert, der Ping-Pong-Effekt stirbt ab und der Nexus-Bus wird wieder ruhig.

9.6 Der Personal Trade Assistant (PTA): Architektur & Event-Sourcing

Der PTA repräsentiert eine spezialisierte Ausprägung des Agenten-Modells, fokussiert auf hochrobuste Exekution und Event-Sourcing anstelle von abstrakter Wissensverwaltung. Er ist das ausführende Organ (Der "Muskel") für den Smart Trade Manager (STM).

9.6.1 Event-Sourcing Datenmodell (Single Source of Truth)

Die Datenbank-Architektur des PTA weicht radikal von traditionellen State-Machines ab. Anstatt den Status eines Trades (OPEN, CLOSED) in der Datenbank zu aktualisieren, speichert die Tabelle pta_execution_log ausschließlich atomare, unveränderliche Events (z.B. ORDER_SUBMITTED, FILL, CANCEL).

Der aktuelle Zustand eines Portfolios (Equity, Winrate, Active Positions) wird on-the-fly über aggregierende SQL-Views (pta_active_positions, pta_portfolio_summary) berechnet. Dieses Design garantiert mathematische Präzision und eliminiert "State-Drift" zwischen lokaler Datenbank und Broker.

9.6.2 Die "Dumb MCP" + "Background Sync" Architektur

Um das System für LLMs leicht wartbar und maximal ausfallsicher zu gestalten, ist die Ausführungslogik entkoppelt:

  • Das MCP Tool (trade): Dient ausschließlich dazu, die "Absicht" (ORDER_SUBMITTED) in die Datenbank zu schreiben. Es kommuniziert nicht mit dem Broker. Dies hält den MCP-Server extrem schlank.
  • Der IBKR-Sync Prozess (ibkr_sync.ts): Ein minimalistisches Hintergrund-Skript, das im Bot-Container läuft. Es pollt die Datenbank nach ausstehenden Orders, sendet sie über eine TCP-Socket-Verbindung (Port 4002) an den IB Gateway Container und schreibt asynchron empfangene Ausführungen (Fills) zurück in die Datenbank.

9.6.3 Robustheit durch Idempotenz

Der Sync-Prozess ist "Exactly-Once" garantiert. Jeder Fill vom Broker erhält eine eindeutige broker_exec_id. Durch einen UNIQUE INDEX in PostgreSQL kann das Sync-Skript bei einem Neustart blind historische Fills abfragen und in die Datenbank pushen, ohne dass es zu Duplikaten (Double-Counting) kommt.

9.6.4 Live-Portfolio-Synchronisation von Interactive Brokers

Wenn der Nutzer oder ein koordinierender Agent den Live-Status des Portfolios abfragt, wird das MCP-Tool list_active_positions aufgerufen. Um sicherzustellen, dass keine permanente Hintergrundlast oder ein ungewollter Live-Mirror läuft, wird das Portfolio rein auf Anfrage (On-Demand Snapshot) synchronisiert:

  1. Refresh-Trigger: Das MCP-Tool schreibt einen Kontroll-Event des Typs REFRESH_REQUESTED in das pta_execution_log.
  2. Sync-Reaktion: Das Hintergrund-Skript ibkr_sync.ts erkennt diesen Request im nächsten Durchlauf, setzt die Sync-Kennzeichnung und stößt einmalig ib.reqPositions() an.
  3. Snapshot-Verarbeitung: Eintreffende Positionen werden im Speicher gesammelt. Sobald das Event EventName.positionEnd signalisiert, dass der Snapshot vollständig ist, wird die Verbindung über ib.cancelPositions() sofort wieder beendet.
  4. Speicherung & Bericht: Die alte Tabelle pta_ibkr_positions wird geleert und mit dem neuen Snapshot überschrieben. Das MCP-Tool liest diese Daten nach einer Wartezeit von 1,5 Sekunden aus und gibt einen konsolidierten Bericht (Live-Broker-Status + lokal getrackte Trades) zurück.

11. Tiefgreifendes Sicherheits- und Rollenkonzept

Sicherheit ist bei einem digitalen RAG-System Fundament, kein Add-on. Wir applizieren strikt das Principle of Least Privilege.

11.1 Netzwerk-Isolation

Die PostgreSQL-Daten liegen raw im Docker-Volume (openbrain_pgdata). Ein Host-Angreifer ohne DB-Credentials kann diese Files nicht ohne Weiteres parsen. Zugriff erfolgt exklusiv über das Nginx-Gateway.

11.2 Explizite Filter-Logik (Code over Magic)

Das Open Brain verzichtet bewusst auf Datenbank-interne RLS-Policies. Stattdessen wird die Filterung hart im TypeScript-Code der MCP-Server implementiert.

  • Transparenz: Die Abfragen enthalten explizite .eq('agent_id', AGENT_ID) Filter. Wer den Code liest, sieht die Sicherheitsschicht.
  • EA God Mode: Der EA-Agent hat globalen Zugriff (p_agent_id = null), waehrend alle anderen Agenten strikt auf ihre eigene ID limitiert sind.
  • Simplizitaet: Keine Komplexitaet durch JWT-Token-Verwaltung pro Agent oder kryptische SQL-Policies.

12. Wartung: Backup & Wiederherstellung

Ein verlustfreies Backup muss sowohl die Vektor-Daten als auch die JSONB-Metadaten konsistent einfrieren.

12.1 Logische Datenbank-Dumps

Ein atomarer Dump der gesamten Instanz erfolgt per pg_dumpall:

docker exec openbrain-db pg_dumpall -c -U postgres > backup_datum.sql

Dieses Binary generiert rohe SQL-Inserts, die Vektoren, JSONB und Chat-Logs vollständig serialisieren.

12.2 Disaster Recovery

Im Falle eines Hardware-Ausfalls wird das SQL-File per Pipe in einen frischen PostgreSQL-Container eingespielt, was das System bit-identisch rehydriert:

cat backup_datum.sql | docker exec -i openbrain-db psql -U postgres

13.3 Neuen Agenten deployen (Das Fork-Paradigma)

Die Instanziierung eines neuen Agenten (z.B. "Trading-Broker") erfordert exakt diesen pragmatischen Workflow:

  1. Agent-Ordner forken: cp -r agent-ea agent-xyz. Die Identität wird ausschließlich über die config.yaml definiert.
  2. Den MCP-Server forken: Kopiere den Ordner agent-ea/mcp-server zu agent-broker/mcp-server. Füge dort deine dedizierte API-Logik für Drittsysteme (z.B. IB-Broker API) als neue Hono-Endpunkte hinzu. Dieser Server läuft netzwerkisoliert und enthält keinerlei Chat-Logik.
  3. Prompt-Konfiguration als Volume mounten (KRITISCH): Prompts gehören niemals hart in den Code oder als Environment Variables in die docker-compose.yml! Erstelle prompt.txt und metadata-prompt.txt und mounte sie via Docker Volumes als read-only (:ro) in die Bot- und MCP-Container. Das ermöglicht dir, die Prompts jederzeit on-the-fly im Host-Editor anzupassen, ohne Container neu bauen zu müssen.
  4. Container deklarieren: Dupliziere in der docker-compose.yml die Bot- und MCP-Blöcke. Mounte config.yaml als read-only Volume. Der Bot liest MCP-URLs, MQTT-Broker und Agenten-ID automatisch daraus.
  5. Schema-Isolation: Falls der Broker eigene relationale Daten braucht, quetsche sie nicht in die Core-Tabellen. Erstelle per Supabase Studio ein neues Schema (z.B. CREATE SCHEMA broker;). PostgREST spiegelt dieses Schema sofort in eine isolierte REST-API.
  6. Starten & Erkennung: docker compose up -d --build agent-xyz-bot. Der neue Agent verbindet sich via MQTT, sendet sein Online-Signal und erscheint dank der automatischen MQTT-Discovery sofort als Checkbox im Dashboard, ohne dass vorher Nachrichten ausgetauscht werden müssen.

13.4 Hot-Reloading via rebuild-agents.sh

Bei Änderungen an TypeScript-Dateien der MCP-Server oder Bots muss der Code neu kompiliert und die Container neugestartet werden. Dafür existiert das Skript rebuild-agents.sh (auch per bash_alias rebuild_agents verfügbar) im Root-Verzeichnis. Es baut die Deno-Images via Docker-Bake im Cache, startet die MCP-Server neu, lädt die Bot-Container neu und flushed den SQL-Schema-Cache von PostgREST. Dies ermöglicht einen Hot-Reload des Systems innerhalb weniger Sekunden, ohne Docker komplett herunterzufahren.
